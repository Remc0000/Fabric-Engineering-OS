# FDR-0002: Governed Project Bootstrap Helper

This decision is governed by the root [Fabric Engineering OS Constitution](../CONSTITUTION.md).

## Status

Proposed for human approval in the pull request that implements issue #25.

## Context

The manual new-project checklist is authoritative but requires adopters to create the same initial consumer documents and evidence placeholders repeatedly. A helper can reduce setup errors, but it must not hide changes, overwrite work, configure remote controls, invoke unpinned tools, or imply approval.

## Decision Drivers

- Preserve the manual bootstrap guides as canonical.
- Default to a deterministic no-write plan.
- Keep generated content outside OS canon.
- Refuse silent overwrites and unsafe paths.
- Make reruns and rollback predictable.
- Avoid package dependencies and work on the repository's existing PowerShell runtime.

## Options Considered

1. **GitHub workflow:** convenient for hosted repositories but requires permissions and cannot configure all protected settings safely.
2. **Cross-platform PowerShell helper:** runs locally and in CI, uses the existing toolchain, and can expose every planned change before writing.
3. **Full project generator:** could initialize tools and settings but creates excessive authority and hidden side effects for a preview OS.

## Decision

Provide `bootstrap/Initialize-FabricProject.ps1` with explicit `Plan`, `Apply`, and `Rollback` modes. `Plan` is the default and performs no writes. `Apply` creates three deterministic files under `consumer/<project-slug>/` or `examples/<project-slug>/`. Existing identical files are unchanged; differing files are conflicts and are never overwritten.

The helper records the selected Spec Kit release and exact initialization commands but does not execute Spec Kit, change GitHub settings, deploy, merge, or contact Fabric. `Rollback` removes only unmodified files generated by the helper and removes only the now-empty project directory.

## Consequences

- Adopters receive consistent project, evidence, and specification-approval scaffolding.
- Repository settings, tool execution, and approvals remain visible manual work.
- The helper intentionally supports a small file contract; extending it requires schema, compatibility, and rollback review.
- A dirty Git working tree blocks writes unless a human explicitly passes `-AllowDirtyWorkingTree`.

## Validation

Test plan-only behavior, fresh apply, deterministic rerun, partial setup, unsafe paths, conflicting content, dirty Git state handling, and rollback.
